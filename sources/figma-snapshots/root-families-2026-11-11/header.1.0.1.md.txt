# header1.0.1

Contrato normativo de diseño y función; observaciones y recetas permanecen referenciales.

### REQ-API

Un principal Header sin variantes. Conservar seis propiedades propias: Show version, Show company, Show actions, Show user y Show release badge BOOLEAN true; Version TEXT 2.0.0. Conservar exposición de logo, Badge, Header actions, Company selector y User selector. Release badge y sus iconos/Label se editan en Badge anidado, no existe propiedad propia Release badge TEXT. Show release badge está subordinado al bloque Show version; no inventar independencia de controles ni API de logo-categoria.

### REQ-ANATOMY

Orden: logo de producto y Content(Version[Version info(Version, Release badge), Divider], Actions[Header actions, Divider], Company[Company selector, Divider], User interaction[User selector]). User interaction es un wrapper transparente HUG con spacing-none; el clic del consumidor vive en el wrapper para conservar el hover del hijo. Los divisores pertenecen a sus bloques y se ocultan con ellos; no añadir lógica de separación condicional inexistente ni menú móvil. Mantener composición por instancias, sin aplanar ni duplicar dibujos.

### REQ-LAYOUT

Ancho inicial1280 y mínimo1152 por elección humana; padding24 y altura96. Conservar Root HUG, SPACE_BETWEEN y bloque derecho HUG; fijar el logo a48px mediante token para sostener96px aunque se oculten todos los bloques derechos. La raíz anterior min1024 podía solapar logo176 + Content887 + padding48. Con la configuración fuente,1152 deja41px entre bloques, al menos40. Es el mínimo de esta configuración; el consumidor debe ampliar el ancho si otro producto, versión o badge incrementa los intrínsecos. No reducir ni recortar el logo o inventar un breakpoint. Las dimensiones del asset conservan su proporción; únicamente horizontal corresponde al Header.

### REQ-ASSET

Reutilizar como asset vinculado el logo contables/contabilidad/horizontal con key e1770fa0d28362f0b2f2045caab556a5d18b7158. Su API real es product y type; el origen no tiene categoria=cuatro-temas. Los cuatro ejemplos conservan ese producto al cambiar de tema: no inventar cambio automático de logo. Conservar el arte y sus colores, sin reconstruir vectores, recolorear la marca o tokenizar su dibujo interno. Registrar key/remote y procedencia después del import en destino.

### REQ-TYPOGRAPHY

Version usa Manrope Regular16/24, tracking0px equivalente al0% fuente; un estilo propio vinculado. Badge conserva tipografía de su contrato. No copiar fuentes/colores de Avatar, Dot ni selectores al padre.

### REQ-DEPENDENCIES

Componer HEADER-ACTIONS-0012.0.0, COMPANY-SELECTOR-0011.0.0, USER-SELECTOR-0011.0.0 y BADGE-0011.1.0 info/medium. Las dependencias Avatar/Dot son transitivas. No alterar sus principales ni copiar tokens de hijos. ### REQ-TOKENS

Quince firmas propias bajo header/ en component. Las cuatro partes comparten el grupo header, sin crear colecciones por subcomponente. BLUEHEART-TOKENS6.9.0 incorpora Icon Button oficial y retira11 firmas privadas sustituidas:812 tokens,163 primitivas,124 semánticos,525 de componente. Header y sus selectores conservan sus firmas; Header actions conserva2 espaciados y delega el control a Icon Button. El corte6.8.0 se conserva como historia. Valores y aliases pertenecen al token set seleccionado.

El badge de etapa corresponde a versiones preliminares, y se oculta en estables por el consumidor. No añadir más de cinco acciones ni destinos que la fuente no define. Los datos fiscales/cuenta deben venir del contexto autorizado del producto; las demostraciones usan ejemplos sintéticos.

### REQ-PROTOTYPE

El host de muestra demuestra apertura/cierre de empresa/cuenta, elección de empresa ficticia y feedback de acciones, sin recargar contexto real ni cerrar la sesión de Figma. Los principales mantienen interacciones visuales reutilizables; destinos y menús de muestra pertenecen al consumidor. Los selectores no contienen un menú en su anatomía. La reproducción visible se acredita aparte del grafo y no valida lógica de negocio.
